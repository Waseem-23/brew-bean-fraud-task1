# Decision Log: Leakage-Safe Pipeline (Task 1)

## 1. PII removal

Removed: `customer_name`, `email`, `ip_address`.

The model needs to learn fraud *patterns* (timing, amount, account age), not
who a person is. Keeping personal details would also go against the cafe's
privacy requirement.

Kept: `customer_id` (needed to count a customer's recent orders) and
`transaction_id`. `customer_id` is only a pseudonymous number, not a name.

## 2. Time-based split instead of random split

The data is sorted by `order_time`. The oldest 80% of orders are the train
set and the newest 20% are the test set. The code asserts that
`max(train time) <= min(test time)`.

Why: in production, the model only ever sees the past when it scores a new
order. A random split would let the model train on orders that happened
*after* some test orders, which makes offline results look better than they
will be in real life.

Trade-off: a time-based split gives a harder, more honest score than a
random split. We accept that.

## 3. Features: raw vs engineered

| Feature | Type | Why it helps | How leakage is avoided |
|---|---|---|---|
| `amount` | raw | Unusual amounts can signal fraud | Known at order time |
| `payment_method`, `merchant_category`, `customer_country` | raw | Some channels are riskier | Known at order time |
| `account_age_days` | engineered | New accounts are used for fraud more often | `order_time - account_created_at`, both known at order time |
| `order_hour` | engineered | Odd-hour orders are riskier | Only uses `order_time` |
| `high_amount_flag` | engineered | Turns "is this a big amount?" into a clear signal | Threshold (75th percentile) is learned in `fit()` on train only, then frozen |
| `customer_txn_velocity_24h` | engineered | Many orders in a short time can mean card testing | Counts only the same customer's orders strictly before the current one, within 24 hours |

Why not only raw columns: a raw timestamp or raw amount does not tell the
model much by itself. Engineered features turn them into signals that are
easier to use.

Trade-off: engineered features add complexity and are one more place where
leakage can sneak in (especially velocity). That is why the threshold and
velocity features each have a unit test.

## 4. Leakage guard (`FutureTimestampGuard`)

A custom scikit-learn transformer that checks `order_time` and
`account_created_at`. If any row has a timestamp later than the reference
time (the latest timestamp in the dataset), it raises an error instead of
letting that row into the pipeline.

It protects against bad or wrongly dated rows. The time-based split is what
protects against test information reaching training. The two checks cover
different problems.

## 5. Encoding and scaling

A `ColumnTransformer` handles numeric and categorical columns separately:
`StandardScaler` for numeric, `OneHotEncoder(handle_unknown="ignore")` for
categorical. Both are fitted on the train set only. If a category appears in
test that never appeared in train, it becomes all zeros instead of crashing.

## 6. Known limitations

- The data is synthetic (generated by `generate_sample_data.py`) because real
  data was not available yet.
- When features are computed on the test set, the velocity feature only sees
  test orders, not train history. So test velocity values can be lower than
  they would be in production.
- The guard only catches dates after the dataset's latest timestamp.
